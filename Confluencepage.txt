WS5 – Structured Data Load POC – Azure SQL Data Model & Ingestion
1. Overview

This document captures the current implementation and understanding of the WS5 Structured Data Load POC.

The objective of this POC is to extract structured data from the identified source data and load the required information into Azure SQL using a standalone Python application.

The initial implementation focuses on:

Azure SQL connectivity
SQLAlchemy ORM-based table creation
Engagement data loading
Third-party data loading
Contract master data loading
Foreign-key relationships between the entities
Basic data validation
Establishing a reusable foundation for the remaining structured-data entities

The implementation is intentionally kept as a standalone Python POC without dependency on the wider application/API platform.

2. Current Architecture

4. Authentication and Database Connectivity

The application uses SQLAlchemy to establish connectivity with Azure SQL.

Two authentication modes are supported:

Service Principal

Recommended for automation and non-interactive execution.

SQL_AUTH_MODE=spn

The application obtains an Azure AD access token using:

AZURE_CLIENT_ID
AZURE_CLIENT_SECRET
AZURE_TENANT_ID

The token is then passed to the SQL Server ODBC driver.

Interactive Authentication

Available for local troubleshooting:

SQL_AUTH_MODE=interactive

This uses the user's corporate identity and interactive Azure AD authentication.

5. ORM-Based Table Creation

Instead of maintaining database DDL statements directly in the Python scripts, the POC uses SQLAlchemy ORM models.

The database entities are represented as Python classes.

For example:

class Engagement(Base):
    __tablename__ = "ENGAGEMENT"
	
The ORM metadata can then be used to create the corresponding database tables.

Current table creation approach:

Base.metadata.create_all(bind=engine)

Important Behaviour

create_all() creates tables that do not already exist.

It does not automatically alter an existing table when columns are added or modified in the Python model.

Therefore:

Existing table
     +
New column added to models.py
     ↓
create_all()
     ↓
Existing table is NOT automatically altered

For future schema changes, an explicit migration/ALTER approach or controlled table recreation will be required.

11. Contract Data Loading

Contract data is currently sourced from the Excel worksheet:

Contract level info

The loader:

Reads the Excel worksheet using Pandas.
Identifies the in-scope engagement IDs.
Filters the source data to the agreed POC scope.
Maps source columns to SQLAlchemy ORM attributes.
Creates the CONTRACT objects.
Uses SQLAlchemy session.merge() to perform insert/update behaviour based on the primary key.
Commits the data to Azure SQL.

18. Source-to-Target Mapping Approach

The current approach is:

Source Excel
     |
     | Pandas
     v
DataFrame
     |
     | Column mapping / cleaning
     v
SQLAlchemy ORM Object
     |
     v
Azure SQL Table


The source column names are not necessarily identical to the target database column names.

Therefore, the loader explicitly maps source fields to the corresponding target ORM attributes.

This approach also allows source data cleaning such as:

Handling NaN
Converting values to appropriate types
Trimming text
Limiting text to target column sizes where required
Filtering to the agreed scope
19. Idempotent Loading

The POC uses SQLAlchemy:

session.merge()

for loading records.

The intention is to allow the loader to be executed again without blindly creating duplicate records for the same primary key.

For example:

Existing contract_ref_num = 53557

Run loader again
        ↓
Existing record identified
        ↓
Record updated rather than creating
another record with the same primary key


The exact update behaviour should continue to be validated as the loaders become more complete.

20. Important Schema Management Note

The current ORM approach is suitable for the POC, but Base.metadata.create_all() should not be considered a database migration mechanism.

If an existing table needs:

a new column
a renamed column
a changed data type
a removed column
a changed constraint

then a controlled schema migration/recreation approach is required.

This is particularly important because the POC is expected to evolve as the final source columns become available.


21. Current POC Design Principle

The current implementation deliberately follows a small-scope-first approach:


Confirm source data
       ↓
Create ORM model
       ↓
Create target table
       ↓
Load limited records
       ↓
Validate relationships
       ↓
Confirm with business/team
       ↓
Expand scope



This prevents thousands of source records from being loaded before the target structure and relationships are confirmed.
