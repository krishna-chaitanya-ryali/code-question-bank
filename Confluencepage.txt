Current Database Structure / Relationship Understanding
For the current POC, we have created and populated the following core tables in Azure SQL:
1. ENGAGEMENT
This is the parent/master table for engagement information.
Primary Key: engagement_id
Contains engagement-level information such as engagement name, supplier key, status, category, business service information, etc.
Currently populated with the three agreed in-scope engagement records.
2. THIRD_PARTY
This table represents the supplier/third-party information.
Primary Key: third_party_id
Currently populated with the required third-party records.
The third_party_id corresponds to the supplier identifier such as tpp-319827 and tpp-282191.
3. CONTRACT
This table contains contract information associated with an engagement and a third party.
Primary Key: contract_ref_num
Foreign Key: contract_engagement_id → ENGAGEMENT.engagement_id
Foreign Key: contract_third_party_id → THIRD_PARTY.third_party_id
Contains contract-level information such as contract ID, contract name, description, status, termination details, regional coverage, etc.
Therefore, each contract is associated with:


One Engagement
       +
One Third Party
       =
Contract


For the current POC, we have successfully loaded 7 contract records across the three in-scope engagements.
Relationship Flow
The current relationship is understood as:


ENGAGEMENT
   |
   | 1-to-many
   |
   +--------> CONTRACT <--------+
                 |              |
                 |              |
          FK: contract_         FK: contract_
          engagement_id         third_party_id
                 |              |
                 v              v
             ENGAGEMENT     THIRD_PARTY

more simple 


ENGAGEMENT
    |
    | engagement_id
    |
    v
CONTRACT
    ^
    |
    | third_party_id
    |
THIRD_PARTY


So, ENGAGEMENT and THIRD_PARTY are the parent/reference entities, and CONTRACT acts as the entity that links a particular engagement with a particular third party.
